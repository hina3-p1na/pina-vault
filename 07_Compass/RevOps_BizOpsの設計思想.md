# RevOps / BizOps の設計思想

## なぜRevOpsに惹かれるか
RevOpsは「営業数字を上げる」ための仕組みではない。
**顧客が価値を受け取るまでの全プロセスの構造的整合性**を担う役割だ。

## 思考の軸

### 従来のSiloモデル（問題の構造）
```
Marketing → MQL数 → Sales → 受注数 → CS → 更新率
（各部門が自分のKPIを最大化 → 全体最適を誰も見ていない）
```

### RevOps的な統合モデル
```
Customer Journey全体 → Value Delivered at each Stage
                    → Conversion Health
                    → Revenue Predictability
```

## 繰り返し発見するパターン
- **Lead → Revenue の変換効率**より**なぜ変換されないか**を問うべき
- Pipeline Velocityを上げる前に**Stage Definition（定義の整合）**を揃えるべき
- CRMデータが汚い理由は「営業が入力しない」ではなく「設計が現場ワークフローと合っていない」

## RevOpsで定義すべき4つの整合性
1. **Data Alignment** — 全チームが同じ定義・同じ数字を見ている
2. **Process Alignment** — ハンドオフが明確でデータが落ちない
3. **Technology Alignment** — ツールが仕事を補助している（逆ではない）
4. **Goal Alignment** — 各チームのKPIが顧客価値と接続されている

## 個人的な仮説
> 「RevOpsの成熟度は、組織がどれだけ"顧客の視点"でパイプラインを設計できているかと相関する」

## アクション・レンズ
- 新しい会社・部署を見るとき: KPIの設計を見ればカルチャーがわかる
- 改善を入れるとき: データの定義から入る、施策から入らない

# Vault運用設計 v2（フォルダ構造・格納ナレッジ・流入プロトコル・AI接続）

> 8本の参考文献の壁打ちを経て確定した、Obsidian Vaultの新しい運用設計。旧`ChatGPT_log`/`Claude_log`/`_state`方式（[[参考文献_抽象化サマリー]]参照）は本設計に置き換わる。
>
> **2026-07-17改訂**：ノートの結節方式を「タイトル完全一致のwikilink」「`#気づき/xxx`的なネストタグ」から、**文章内の自然なキーワードに対するインラインwikilink**（2章参照）へ転換。あわせて、07_Compass/08_Businessで「1テーマ1ファイルに会話要約を延々追記する」累積ログ方式をやめ、**1会話・1セッション＝1アトミックノート**に分解する方式へ転換（1章・2章参照）。理由：会話要約が薄くなりすぎて気づきのストックとして機能していなかったこと、タイトル完全一致のリンクは表記が変わるたびに壊れ、ふとした気づき同士が自然に結節しないこと。

---

## 0. 位置づけの大前提

- **Obsidian** ＝第二の脳そのもの。思考・思想・アイデア・ノウハウ・興味関心・振り返り・経験の蓄積場所（脳内メモ・素材・思考整理の場所）
- **Claude Code** ＝その記憶を読んで判断・作業を引き継ぐ処理レイヤー（※現時点では未導入。バックボーンはCoworkのまま）
- **NotebookLM** ＝Obsidianの一部（脳内メモ＋関連文献）を都度テーマ単位で投げ込み、高純度な分析・新しいアイデア抽出を行う作業台。常時同期する倉庫ではない
- **Notion** ＝タスク管理・会議の生ログ
- 生ログ（会話・議事録・タスク）はObsidianに原則残さない。残すのは「自分の解釈・気づき・型化が乗ったもの」だけ。手順書化できたものはNotionへ逆輸入する導線を持つ

## 1. フォルダ構造

物理フォルダ（MECEな箱）＝情報の成熟度で分ける。テーマ横断のつながり（タグ・リンク）は箱の外で表現する。

| 番号 | フォルダ | ライフサイクル上の位置 | 何が入るか |
|---|---|---|---|
| 00_Personal | Profile / Career / Private | 土台 | 自己定義・キャリア開発メモ・仕事に関係しない私事 |
| 01_Inbox | — | 集める（自分発） | 自分の思いつき・気づき・断片。未整理でいい |
| 02_Resources | Library / Clipping | 集める（外部発） | 読書メモ／外部記事・YouTube等の原本。自分の解釈は加えない |
| 03_Research | — | 整理する | 01・02をAIが要約・統合した中間生成物。元素材へのリンク必須、元素材は書き換えない |
| 04_Journal | Daily / Weekly / Monthly | 記録する | 日々の記録から週報・月報へ昇華 |
| 05_Seeds | — | 種にする | まだ育ってない気づきの断片・切り口 |
| 06_Brainstem | — | テーマ横断のハブ（MOC） | **実体を持たない。リンクのみ。** 00/01/02/05/07/08の関連ノートを1テーマに束ねる |
| 07_Compass | — | 実にする | 確定した気づき・判断基準・価値観・行動基準・志向性。「現時点の理解」を保持する生きたサマリーノート（後述） |
| 08_Business | — | 完成（業務記録） | 案件・組織の状態記録（「事実」であって「自分の解釈」ではないもの）。「現時点の理解」を保持する生きたサマリーノート（後述） |
| 09_Archive | — | 役目を終えたもの | 削除せず移動 |
| _Template | — | — | テンプレート書庫 |
| _System | — | 取扱説明書 | 運用ルール・HarnessOps設計図・スケジュールタスク定義。人間は普段開かない |

### 判断基準（情報の成熟度ラダー）
03_Research（自分の意見ゼロ、事実の整理のみ）→ 05_Seeds（関心はあるが結論はまだ）→ 07_Compass（繰り返し確認された確信・判断基準）。06_Brainstemはこのラダーとは別軸（横のつながり）。

### 対話セッションノートの扱い（2026-07-17改訂）
AI壁打ち・MTGから distillation された気づきは、**1会話・1セッション＝1アトミックノート**として書き出す。1つのファイルに複数セッションの要約を時系列で延々追記する旧タイムライン方式（1会話あたりの記述が一行程度に圧縮され、気づきのストックとして機能しなくなっていた）はやめる。

- 保存先は内容の成熟度ラダーに従って01_Inbox／05_Seeds／07_Compass／08_Businessのいずれかへ、そのまま個別ノートとして置く（圧縮しすぎず、気づきの実質的な情報量を保つ）
- 07_Compass・08_Businessの既存テーマノート（例：[[組織・評価制度設計]]）は、個別セッションノートを追記される場所ではなく、**それらを統合した「現時点の理解」を保持する生きたサマリーノート**として役割を絞る。テーマと個別セッションノートの紐付けは、後述する自然文キーワードリンクとバックリンクによって成立させる（ファイルを1つにまとめることでテーマを表現しない）
- 06_Brainstemのハブノートが「累積更新」なのは変わらない。ハブは実体を持たずリンクを束ねるだけなので、更新されても対話ログの蓄積とは性質が異なる

### 既存フォルダの移行方針
- `思い付きのアイデアメモ/` → 01_Inbox へ統合
- `chat_stock/` → 「自分の解釈・思考が乗っているもの」は05_Seeds/07_Compass、「案件・組織の状態記録」は08_Business へ振り分け
- `mtg_stock/` → 蒸留された気づきのみObsidianへ、生ログはNotion側に残す
- 既存`01_Insights`→07_Compassの一部として統合検討、`02_Decisions`→07_Compass、`03_Themes`→06_Brainstemのハブノートとして再構成、`04_Goals`→08_Business

### フォルダ設計に関する留意事項（動画から得た教訓）
- テーマ（意味内容）でフォルダを分けない。分けているのはあくまで「情報の成熟度」「形式」であり、これらは判断にほぼ迷いが生じない軸
- 08_Businessや07_Compassの中を将来「テーマ別サブフォルダ」で分けたくなっても、やらない。テーマの整理は06_Brainstemのリンクに任せる

## 2. 格納ナレッジ（ノートの粒度・タイトル・タグ・リンクのルール）

| フォルダ | 1ノートの単位 | タイトルの付け方 |
|---|---|---|
| 01_Inbox | 1回の思いつき＝1ノート（アトミック） | 日付なしの短い見出し（例：ふと思ったこと。日付情報はfrontmatterのcreatedで保持し、ファイル名には含めない） |
| 02_Resources | 1つの外部ソース＝1ノート | ソースのタイトルそのまま |
| 03_Research | 1つの調査テーマ＝1ノート（複数ソース統合） | テーマ名＋調査時期 |
| 04_Journal | 1日／1週／1月＝1ノート（累積更新） | ISO日付（2026-07-15／2026-W29／2026-07） |
| 05_Seeds | 1つの気づきの断片＝1ノート（アトミック） | 気づきを文で表現 |
| 06_Brainstem | 1テーマ＝1ハブノート（累積更新） | テーマ名 |
| 07_Compass | 1つの原則・判断基準＝1ノート（生きたノート、更新される。個別セッションの記録は別ノートに分離） | 原則を文で表現 |
| 08_Business | 1案件・1組織テーマ＝1ノート（「現時点の理解」を保持する生きたサマリーノート。個別セッションの記録は別ノートに分離） | クライアント名｜そのエンゲージメントの核（例：カミナシ｜属人化した支援を型に変える。「〇〇プロジェクト」「〇〇運営」等の量産的な語尾は避ける） |
| （対話セッションノート） | 1会話・1セッション＝1アトミックノート | 会話の内容を文で表現（テーマ名の量産的な連番タイトルは避ける） |

**ノート同士の相関＝自然文キーワードのインラインwikilink**（2026-07-17改訂）：
- ノートの結節は、別建てのタグブロックやタイトル完全一致リンクではなく、**本文の地の文の中に出てくるキーワード・概念語を、その場で自然に`[[キーワード]]`としてインラインリンク化する**ことで作る。「〇〇という概念」「〇〇な状態」のような一般的な言い回しではなく、繰り返し出てくる固有の概念・判断基準・案件名・人物特性など「それ自体が独立した概念ノートとして存在する（べき）語」にのみ貼る
- リンク先の概念ノートが存在しない場合、AIがごく短い概念ノート（定義1〜2行＋関連ノートへの導線）を新規作成する。次に同じ概念が出てきたときはそのノートへ自然にリンクさせ、結果としてバックリンク・グラフビューがそのままキーワード相関のハブになる
- 概念ノートの置き場所は成熟度ラダーに従う（判断基準・原則級の概念は07_Compass、案件固有の概念は08_Businessなど）。06_Brainstemのハブノートは、この自然発生した相関の中でも特に太い束を人間が意図的に選んでまとめる場所として残る

**タグ**：ソース種別（`#ソース/クリッピング` `#mtg` `#chatgpt`等）の薄いラベルとしてのみ使う。概念・テーマの相関はタグではなく上記のインラインwikilinkで表現する（`#気づき/xxx` `#テーマ/xxx`のようなネスト概念タグは廃止）

**表記ゆれ対策**：
1. 概念には正式な1つの概念ノート名を決め、フロントマターの`aliases`に言い換えを登録
2. 新規リンクを貼る前に類似ノート（概念ノート含む）の有無をAIが検索してから作成（流入プロトコル側のルール）
3. 最終的な検索の主役は06_Brainstemのハブノートと概念ノートのバックリンク。wikilinkの完全一致に検索性を依存しすぎない

## 3. 流入プロトコル

| フォルダ | トリガー | 頻度 |
|---|---|---|
| 01_Inbox | Slack自分宛メッセージ（URLを含まないもの）／AI壁打ちセッションから抽出した生煮えの断片 | 日次（夜間スイープ） |
| 02_Resources | Slack自分宛メッセージ（URLを含むもの）を自動取得・保存 | 日次（同上） |
| 03_Research | 02_Resourcesに同テーマの素材が複数溜まったらAIが要約・統合 | 週次 |
| 04_Journal | 当日のNotion MTGログ＋AI壁打ちの成果＋Inbox/Clippingsの当日分から日報を自動下書き | 日次（夜間） |
| 04_Weekly/Monthly | 日報の蓄積から自動要約 | 週次／月次 |
| 05_Seeds→06_Brainstem/07_Compass | AIが「複数回パターンとして出てきた」候補を検出し昇格提案 | 週次 |
| 08_Business（対話セッションノート） | 既存のMTGログBOX同期の仕組みに乗せ、案件と紐づくMTGログの更新時に、**後述のフィルタ基準を満たした場合のみ**新規の1セッションノートとして書き出す（既存テーマノートへの追記はしない）。AIが本文中のキーワードを検出しインラインwikilink化、該当する08_Businessテーマノートの「現時点の理解」を更新提案 | MTGログ更新のたび |
| 09_Archive | 一定期間（目安3ヶ月）更新のないノートをAIが検出し、まとめて提案 | 月次 |
| Notionへの逆輸入 | Obsidian側で「再現性のある手順」と判断されたものをNotionのSOPへ書き戻す | 都度判断（AI提案→承認） |

**承認フロー**：夜間スイープの結果はSlackに1日1通のサマリーとして送る（「今日の取り込み：Inbox3件・Seeds1件・日報下書き1件」）。気になった項目だけ返信で修正、無反応なら自動確定。通知を分散させない。

### MTGログ→セッションノート化のフィルタ基準（2026-07-18改訂：3層トリアージモデル）

0章の原則「生ログは残さない。残すのは自分の解釈が乗ったものだけ」を、08_Businessセッションノート化の場面で機能させるための具体的な仕組み。42件のMTGログ由来ノートを棚卸しした結果、活動量・KPI数値・他者の発言記録・合意事項の列挙だけのノートが約4割を占めていた。AIがそれらしい解釈風の言い回しを添えていても実質的な内省がなければ「第二の脳」として機能しないこと、また「Notion発かどうか」という情報源では層別できない（1on1やKPIレビューのように、業務MTGの体裁でも中身が内省寄りのことがある）ことが判明したため、**情報源ではなく会議の性質と中身**で判定する2段構えに改訂した。

**一次トリアージ（会議の性質による3層分類）**：MTGログが更新されたら、まずどの層に該当するかを機械的に判定する。

| 層 | 該当する会議の例 | 扱い |
|---|---|---|
| 層1：ほぼ確実に事実のみ | 説明会・制度説明・事務確認・単純な進捗共有のデイリー | 蒸留を試みない。Notionのみに残し、Obsidianへは書き出さない |
| 層2：内省が生まれやすい | 1on1・育成面談・壁打ち・振り返り・方針転換の意思決定の場 | 積極的に蒸留を試みる。ただし下記の判定テストは省略しない |
| 層3：中身次第のグレーゾーン | KPI/営業活動レビュー・商談ログなど | 判定テストを厳格に適用し、迷ったら書き出さない側に倒す |

**二次判定（層2・層3に適用する判定テスト）**：その打ち合わせについて、以下のいずれかが本人の言葉で具体的に書けるか？
- なぜそう考えたか・そう判断したかの理由づけ
- そこから得た気づき・学び・今後への転用可能な教訓
- 働いた判断基準・価値観
- 印象に残った感情・体験

満たさない場合（活動量やKPI数値、事実確認、他者の発言記録の要約のみ）は、Obsidianには書き出さず、Notion側の議事録のみに残す。既存テーマノートの「現時点の理解」に1行だけ事実として言及するに留めるかどうかは、案件の状態把握上その事実自体が重要かどうかで個別判断する。

**リンク必須化**：判定テストを通過したノートも、本文中に既存の概念ノート（07_Compass/08_Businessの既存テーマ・原則ノートなど）への自然文インラインwikilinkを最低1つ貼れない場合は、その場で書き出さず保留し、Slackの承認フローで人間に確認を挟む。既存の概念に接続できないということは「新しい概念候補」か「単なる断片」のどちらかであり、機械的にどちらか決めつけない。

**層1・判定テスト不合格でも人間が残すと判断した場合の扱い**：後で見返す必要がある計画・条件など、実務上の参照価値を理由に残したいケースはある（2026-07-18の棚卸しで実例あり）。これは「解釈が乗っているか」とは別の軸の判断であり、機械的なルールにはしない。承認フロー（Slack返信での修正）で都度人間が拾う。

**レビュー候補一覧.mdの運用**：週次stock-reviewが出す昇格候補・因数分解候補・アーカイブ候補は、その日のうちに確認できなければ翌週分に上書きされず、未処理のまま一覧に累積させる（項目にチェックが入る＝処理済みとして削除してよい）。

## 4. AI接続（バックボーン）

- **結論**：当面はCoworkのスケジュールタスクを背骨として運用する。Claude Codeへの本格移行はしない
- **理由**：流入プロトコルの主役はSlack・Notion連携であり、これはCoworkのMCP接続と相性が良い。Claude Codeの強み（自律実行・サブエージェント・hookによるセッション引き継ぎ）は、今のところ具体的な困りごとに紐づいていない
- **例外**：NotebookLM連携（`notebooklm-mcp`）は、認証情報をローカルに永続保存する必要があるため、Coworkのクラウドサンドボックス（セッションごとにリセットされる）では原理的に成立しない。ぴなちゃんが自分のPCのターミナルで`pip install`→`nlm login`→`nlm doctor`を一度だけ実行すれば、以降はCowork経由でも間接的に活用できる見込み。優先度は低く、必要になったタイミングで着手する
- **原則**：外部ノウハウ・新しいツールは「バズっているから」ではなく「自分の困りごとに対応する形で1つずつ」導入する

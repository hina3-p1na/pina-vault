## 2. 共通して言われていた原則（重要度順）

### 原則1：フォルダは目的の逆算であり、目的は「何を管理しないか」から決まる（rock72）
最初に「これはObsidianで管理しない」と決めたものがある人ほど、フォルダが機能している。全部を溜め込もうとすると破綻する。
→ ぴなちゃんの場合、今のVaultは「何でも入れる」状態になっていて、この逆算が一度もされていない。

### 原則2：情報の"入口"は性質で分ける（みなみ氏、rock72、agexworks 共通）
自分の一次情報（思いつき・気づき）と、外部から持ってきた借り物の情報（記事クリップ、AIとの会話ログ）は、生まれた瞬間から置き場所を分ける。混ぜると「自分の思考」なのか「誰かの受け売り」なのか後から判別できなくなる。
→ 今のVaultの`00_ref/chat_stock`はこの2つが混在している疑いがある。

### 原則3：番号は情報のライフサイクルをそのまま表す（axel8、みなみ氏）
集める → 整理する（AIが要約・翻訳） → 記録する（Daily/Weekly） → 種にする（テーマの萌芽） → 完成（アウトプット）。番号は「見た目の整頓」ではなく「情報が育つ順番」を表すためにある。
→ 今の`00_〜04`の番号は、思考の成熟度（Profile→Insight→Decision→Theme→Goal）を表していて、これはこれで一貫している。ただし「集める→整理する」という手前の工程（Inbox的な層）が明示的に存在しない。

### 原則4：ツールは1つに寄せない。得意分野で意図的に分散する（みなみ氏①③）
メモ・素材・思考の整理＝Obsidian／タスク管理・会議の記録＝Notion／アウトプット生成＝Claude Code等、と役割を切る。これは効率だけでなく「1つのツールが落ちても止まらない」ためのリスク分散でもある。
→ ぴなちゃんは既にNotion（タスク・MTG）とObsidian（知識）を分けている。ここは既に原則に合致している。

### 原則5：Obsidianを複数AIの「共通の記憶」にする（みなみ氏②）
ツールごとに必要なのは「入口ファイル」（Claude Code用のCLAUDE.md、Codex用のAGENTS.md等）だけで、素材そのものとルールは共通化する。片方のAIが止まっても、もう片方で続けられる。
→ 今はCowork（Claude Desktop）に一本化されている。将来Claude Codeを併用するなら、この発想が効いてくる。

### 原則6：AIの運用ルール・裏方ファイルは、人間が見る領域と完全に分離する（新居氏、みなみ氏）
`.claude/`のような専用領域に隔離し、「取扱説明書」として扱う。人間は普段そこを開かない。
→ 今回作った`00_ref/_state/`はこの発想の実装だったが、ぴなちゃんの「イメージ違う」はおそらくこの分離の"場所"や"見え方"に違和感があった可能性が高い（後述）。

### 原則7：ルールには強弱をつける（新居氏）
「絶対厳守」と「できれば守ってほしい」を書き分ける。AIに重要度を認識させるには、人間の感情の文脈（「これは何度も指摘した」等）まで書き込む必要がある。
→ 今のプロフィール系ノートは特性の記述はあるが、指示の強弱付けはまだされていない。

### 原則8：止めるべき瞬間とAIに任せてよい瞬間を、事前にリスト化しておく（新居氏）
🔴常に止まる（方針転換・不可逆な決定・対外発信）と🟢止まらない（調査・下書き・自己修正可能な軽微作業）を分けておくと、AIが自律的に動ける範囲が明確になり、逆に人間の確認コストが下がる。
→ 今は暗黙的（都度判断）。明文化されていない。

### 原則9：一度の間違いは仕方ない、二度目を防ぐために"即"記録する（新居氏 MEMORY.md）
致命的・不可逆な事実（例：本番環境情報、絶対NGな判断）は、間違いが起きた瞬間に恒久記憶へ書く。今のVaultでいう`00_Profile`やHarnessOps進捗管理がこれに近い機能を持っている。

### 原則10：外部の型を無批判にコピーしない（新居氏、本人の自戒として最重要）
「バズっていたから」ではなく「自分の困りごとに対応する形で1つずつ」導入する。新居氏本人も、他人のスキルセットをそのまま輸入してVaultのリンク構造を壊した失敗を明言している。
→ ぴなちゃんの「AI原始人」という自己認識と直接関係する原則。8本の記事の中でエンジニア色が最も強い新居氏の構成（80スキル・11サブエージェント・自作ダッシュボード）は、そのまま真似る対象ではなく「発想のカタログ」として参照するのが妥当。

### 原則11：NotebookLMとObsidian×Claudeは役割が違う（動画）
NotebookLM＝フロントエンド（速い・出典付き・その場のキャッチアップに強いが、長期定着には弱い）。Obsidian×Claude＝バックエンド（遅いが、書けば書くほど資産が複利で効いてくるセカンドブレイン）。両方を持つ意味は「知らないことを速習する層」と「知っていることを育てて使い倒す層」を分けること。

## 3. 今回の「イメージ違う」の正体（推測）

前回作った`ChatGPT_log.md`/`Claude_log.md`/`_state/`は、原則6（裏方の隔離）と原則3（ライフサイクルの番号化）を個別には満たしていたが、**原則1（何を管理しないか）を先に決めずに作った**ため、「本当にこれは自分が読み返す価値のある記録なのか」が曖昧なまま構造だけ整えてしまった可能性が高い。次にやるべきは、先に構造を直すことではなく、**「AIとの会話ログを、そもそもストックする意味があるのはどんな時か」を先に決めること**。

## 4. 技術的な制約（先に共有しておきたいこと）

動画で紹介されている`notebooklm-mcp`（非公式CLIツール）は、`pip install`→`nlm login`（Chrome起動・Google OAuth）→`nlm doctor`という手順で、**ぴなちゃんのPC上のターミナルで一度ログインを済ませる必要がある**。私（Claude/Cowork）が今動いているのはクラウド上の隔離されたサンドボックスで、ここでログインしても保存先がぴなちゃんのPCではないため、セッションを跨いで使い物にならない。
つまりこの連携は「Coworkにお願いすれば裏側で全部やってくれる」形にはならず、最初の認証だけはぴなちゃん自身がローカルのターミナルで行う必要がある（その後の日常的な操作はClaude経由でできる、という設計）。ここは正直に共有しておきたいポイント。
